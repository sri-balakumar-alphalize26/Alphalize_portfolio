## Why this session exists

The 369 site had an SEO pass on 11–12 September (`cdfde61`, `c94d26c`, `e51d5b7`, `4278189`) — sitemap, robots, a generated share card, a favicon set, brand-entity disambiguation, Product/Breadcrumb/ItemList schema. The ask was to bring the same here.

This site is **not** starting from zero. `a50a436 "SEO added"` already shipped canonical + hreflang across all nine locales with `x-default`, OG/Twitter tags, a sitemap with `xhtml:link` alternates and a git-derived `lastmod`, robots.txt, and Organization/LocalBusiness + WebSite + BreadcrumbList + AboutPage + ContactPage + Person + JobPosting + Service + ItemList JSON-LD.

So this is a **delta pass**: fix what is wrong, port the four things the 369 site has and this one does not, add the measurement layer neither site has.

Scope was narrowed mid-session on instruction: **SEO only — no functional or UI changes.** Two items were dropped as a result, recorded at the bottom.

## Done

### The services `ItemList` published English URLs in all nine locales

`src/pages/[locale]/services/index.astro` built `url: ${site.url}/services/${s.slug}` — no locale segment. Every one of those URLs 301s through `public/_redirects` before it resolves, so all nine locales advertised the same seven English URLs in their structured data. A list of nine identical URLs tells a crawler the nine pages are one page, which is the exact opposite of what the hreflang set beside it says.

Now `new URL(localeHref(locale, '/services/' + s.slug), site.url).href`, matching every other JSON-LD block on the site.

This one was known: `369ai_portfolio/lib/structured-data.ts` cites it by name, twice, as the reason its own helpers take `locale` as a required parameter rather than an optional one.

### All nine home pages carried identical English metadata

`src/pages/[locale]/index.astro` passed a template-literal title and the `site.description` **constant** from `src/config/site.ts`, bypassing the catalogues entirely — even though a translated `site.description` exists in all nine. Nine hreflang alternates, one language of metadata.

Now `t('site.metaTitle')` and `t('site.description')`.

`site.metaTitle` is a new key, added to all nine catalogues in the same change (`check-i18n.mjs` treats a missing key in a `liveLocale` as fatal, so it could not be staged). English value is `Alphalize — ERP Solutions & Business Intelligence` — the string that was hardcoded, kept because it names what people search for. It is deliberately **not** `site.tagline`: "Unlocking Growth Potential" is how the work is sold, not what it is called.

The brand stays inside the string because `Seo.astro:65` gives the home page a bare title with no `| Alphalize` suffix.

### robots.txt disallowed nothing

Four lines: `Allow: /` and the sitemap. Three surfaces that exist here were unlisted:

```
Disallow: /api/                      # /api/cv/* streams applicant CVs
Disallow: /*/careers/applications    # the applicant inbox, one path per locale
Disallow: /*?manage=                 # a real URL a crawler could follow
```

About indexing, not access — the session cookie is what protects these.

### One favicon at 40×40

Every icon surface was upscaling a 40px PNG, or falling back to nothing: a tab wants 32, a bookmark 128, iOS a 180 `apple-touch-icon`, Android a maskable 512.

`scripts/generate-icons.mjs` (new, ported from the 369 site's) now emits three, from the mark at the left of `src/assets/brand/logo.png`:

| File | Size | Background | Inset |
|---|---|---|---|
| `public/favicon.png` | 512×512 | transparent | 6% |
| `public/apple-touch-icon.png` | 180×180 | **solid white** | 10% |
| `public/icons/maskable-512.png` | 512×512 | solid white | 20% |

The white on `apple-touch-icon` is not cosmetic — iOS composites transparency onto **black**, and the mark is dark blue. The fat maskable inset is because Android crops to the launcher's shape.

The crop is measured, not guessed. Ink in `logo.png` runs columns 9→855, and the only gap wider than 10px sits at 230–244 — the space between the mark and the "alphalize" wordmark. So the mark is the leftmost 240×240, and a wordmark squeezed into a 32px square never happens.

Source is only 240px, upscaled to 512 with lanczos3. Acceptable because the artwork is smooth gradient with no fine detail — but if a larger master ever turns up, re-point `LOGO`/`MARK` and re-run.

### No web manifest

`public/site.webmanifest` (new), plus the three `<link>` tags in `BaseLayout.astro`'s head.

`display: 'browser'` deliberately — this is a marketing site, not an installable app, so an added-to-home-screen shortcut should open in normal browser chrome rather than pretend to be standalone. `start_url: '/en'`, since a manifest is one document for the origin and has to pick a locale.

`apple-touch-icon` is declared as its own `<link>` and not left to the manifest: Safari does not read the manifest for it.

### The Organization node had no `alternateName`

```js
alternateName: ['Alphalize Technologies', 'alphalize.com'],
```

"Alphalize Technologies" is the form on the invoices, the job listings and the LinkedIn page; `name` alone is the trading name, so that query was not matched to this entity. Query variants only — `legalName` is already its own field, and this must not grow into a keyword list.

### Sixteen share cards, one per route

`scripts/generate-og.mjs` ran: `public/og-default.png` regenerated plus fifteen under `public/og/` (`about`, `ceo`, `careers`, `contact`, `services`, `services/<7 slugs>`, `legal/<3 slugs>`), 1200×630, 85–98 KB each, 1.4 MB total. Run three times; SHA-256 of all sixteen identical across runs, so the satori path is deterministic as intended.

One change to the script before the first run: it loads Inter 500 as well as 400/600/700, because the footer line asks for 500 and satori was silently substituting the nearest weight.

Wired with `ogImagePath` on the seven page files listed in the earlier plan. `LegalLayout.astro` gained the prop and forwards it. Home, 404 and the applications inbox fall through to the default card. In the build, `dist/client` references fifteen distinct `og:image` URLs and every one resolves to a file in `public/`; `og-default.png` is referenced by exactly the nine home pages and `404.html`. Contact is rendered on demand, so its card is checked in the server chunk rather than in `dist/client`.

`npm run og` and `npm run icons` are in `package.json`. Not `prebuild` hooks; outputs are committed.

The design decisions are worth not re-litigating:

**satori → SVG with text as paths → sharp → PNG.** One new devDependency (`satori 0.33.4`, pure JS/WASM), already installed.

The alternative — hand-built SVG rasterised by sharp — was rejected on measurement, not taste. sharp *will* render `<text>`, which is the trap: it resolves the family through system fontconfig, so output depends on the machine. On this box `sans-serif` resolves to **Courier metrics**. And the escape hatch is closed — sharp's `fontfile` option silently ignores `.woff`/`.woff2`, producing output byte-identical to passing a deliberately bogus family name. `@fontsource` ships zero `.ttf`, and `packages/astro-marker` holds woff2 only.

satori shapes with harfbuzz and lays out with Yoga, both WASM, and with `embedFont` on it emits every glyph as a `<path>` — so the SVG handed to sharp names no font, librsvg never consults fontconfig, and the bytes are identical across machines. It also reads `.woff`, which is what `@fontsource/inter` actually ships.

The rule that falls out, and the reason the script is split the way it is: **text never goes into a hand-written SVG; geometry never goes into satori.**

**16 English cards, one per route — not per locale.** Per-locale is ~135 PNGs and 10–12 MB of binary committed permanently, rewritten whole on every design tweak. What it buys is small: the seven service pages have English-only titles in all nine locales anyway, so 63 of those files would be byte-identical; and `og:title`/`og:description` in the `<head>` are already correct per locale. The image is the decorative half of an unfurl — the text half is right today. It would also force the six Noto faces plus Arabic bidi into the generator, and a subtly wrong Arabic card is worse than an English one.

The renderer takes a flat descriptor (`card({ eyebrow, title, support, out })`) so a locale loop later is a change to `CARDS`, not to `card()`.

**Card title is the page's H1, not `metaTitle`** — otherwise `careers.png` reads eyebrow "Careers" over title "Careers", and `contact.png` "Contact" over "Contact". The `<head>`'s `og:title` keeps using `metaTitle`, unchanged.

**`og-default.png` is regenerated from the same template**, which also retires a phantom: its footer currently reads `Clearwater, FL · Kollam, Kerala`, but `offices` in `src/config/site.ts` has held exactly one entry since the Florida office came out.

**The logo is deliberately absent from the card.** Both `logo.png` and `wordmark.png` are dark navy on transparency and vanish on a navy ground, and there is no white lockup in the repo (`brand/letters/*.png` are nine individual textured letters for the splash animation; `splash-a/b.png` are single blades of the mark, not a lockup). The card this replaces carries no mark either. Inverting it via `sharp(logo).negate({alpha:false})` is a one-line change if a designer wants it.

To regenerate: `npm run og`.

## Dropped, and why

**Two i18n fixes, cut when scope narrowed to SEO-only.** Both are real and both are still open:

- `src/pages/[locale]/services/[...slug].astro` passes `crumbs={[{ label: 'Services', … }]}` — a hardcoded English label that lands in the BreadcrumbList JSON-LD built in `PageHero.astro`. Eight locales publish an English crumb. `t('nav.services')` fixes it, but it also changes visible breadcrumb text, so it was left alone.
- `src/pages/[locale]/services/index.astro:52` passes a literal English `body` to `<CtaBand>`. Pure UI copy, no SEO weight.

**Four things deliberately not attempted:**

- **FAQPage schema.** There is no question-and-answer content anywhere in `src/`. `WhyCards` and `WhyChooseUs` are value-proposition cards, not Q&A. Marking them up as an FAQ would be a fabrication. Writing real FAQ content is a content job worth doing on its own.
- **Review / AggregateRating.** `src/data/testimonials.json` has no date field at all, all nine ratings are `5` (which is also the schema default), eight of nine names are first-name-only, and the 11 September notes record that seven were written from topics you gave rather than submitted verbatim. Publishing that as `Review` markup invites a manual action. The 369 site has the same data and also did not mark it up.
- **Per-app indexable pages.** The ten entries in `src/content/apps/` are frontmatter-only — title, one-line tagline, three features, and a logo (not a screenshot). No body, no store link. Ten thin pages × nine locales is 90 URLs of near-duplicate English.
- **Translating the seven service pages' titles and descriptions.** The service *bodies* are English-only in all nine locales — `src/content/services/` has an `en/` directory and nothing else. Translating only the `<title>` would pair a Hindi title with an English page, which is treated worse than consistent English. This unlocks once the content itself is translated.

**Cross-site entity markup** between alphalize.com and 369ai.biz was considered and declined. The two share a phone number, an `hr@` address and a header brand switcher, so a `sameAs`/`parentOrganization` link was on the table; decided to leave them as independent entities in schema.
